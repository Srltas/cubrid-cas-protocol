PREPARE_AND_EXECUTE

SQL 문을 준비하고 곧바로 실행해 준비 결과와 실행 결과와 첫 행 묶음을 한 응답으로 돌려준다

비고​

  • prepare_argc_count가 2보다 작으면 CAS는 CAS_ER_ARGS 오류로 응답한다. CAS는 실제 인자 수를 prepare_argc_count와 견주지 않는다.
  • CAS는 prepare_argc_count 뒤의 인자 가운데 앞의 prepare_argc_count개를 PREPARE를 처리하는 fn_prepare_internal에, 그 뒤의 인자를 EXECUTE를 처리하는 fn_execute_internal에 넘긴다. sql_stmt부터 deferred_close_handle까지는 PREPARE가 읽는 것과 같고, execute_flag부터 query_timeout까지는 EXECUTE가 읽는 것과 같다. 응답은 PREPARE의 응답 바로 뒤에 EXECUTE의 응답을 이어 붙인 것이고 EXECUTE의 응답은 row_count부터다.
  • auto_commit_mode 뒤의 PREPARE 인자는 모두 닫을 핸들 번호로 읽고 각 번호의 서버 핸들을 해제한다.
  • prepare_flag에 CCI_PREPARE_UPDATABLE과 CCI_PREPARE_HOLDABLE이 함께 있으면 CAS는 CAS_ER_HOLDABLE_NOT_ALLOWED 오류로 응답한다.
  • CAS는 닫을 핸들을 해제하고 prepare_flag를 검사한 뒤 새 서버 핸들을 만든다. 핸들 수가 브로커 파라미터 MAX_PREPARED_STMT_COUNT에 이르렀으면 CAS_ER_MAX_PREPARED_STMT_COUNT_EXCEEDED 오류로, 메모리가 모자라면 CAS_ER_NO_MORE_MEMORY 오류로 응답한다.
  • CAS는 실행 쪽 인자를 execute_flag부터 query_timeout까지 6개만 읽고 그 뒤의 인자는 읽지 않는다. 실행을 처리하는 함수에 인자 수를 실제 수가 아니라 10으로 넘기고, 바인드 값이 시작하는 자리도 10번째 인자 뒤라서 바인드 값으로 읽을 인자가 없다. 실행에 사용하는 서버 핸들은 준비가 돌려준 핸들이라서 인자로 받지 않는다.
  • EXECUTE 요청에 있는 서버 핸들, fetch_flag, auto_commit_mode, forward_only_cursor 인자는 이 함수에 없다. 첫 행 묶음을 붙일지는 준비한 문장의 종류가 SELECT인지로 정하고, 자동 커밋 모드와 앞으로만 가는 커서 여부는 준비한 핸들의 자동 커밋 모드가 0이 아니면 둘 다 참, 아니면 둘 다 거짓으로 정한다.
  • bind_values는 읽지 않는다. 준비한 문장의 바인드 위치 표시자가 1개 이상이면 CAS는 CAS_ER_NUM_BIND 오류로 응답하므로 표시자가 없는 문장만 실행할 수 있다. 질의 대체 규칙이 맞은 핸들은 원래 질의의 표시자 수가 0보다 크면 같은 오류로 응답한다.
  • param_mode는 핸들을 CALL 플래그로 준비했을 때만 저장 프로시저의 파라미터 모드로 사용하고 아니면 읽고 버린다. execute_flag에 CCI_EXEC_QUERY_ALL이 있으면 SQL 문 전체를 차례로 실행하고, 이때 num_q_result는 실행한 문장 수다.
  • query_timeout이 0이면 CAS는 브로커 파라미터 MAX_QUERY_TIMEOUT(초)을 제한 시간으로 사용하고, 그것도 0이면 제한이 없다. 둘 다 0이 아니면 작은 쪽을 사용한다.
  • max_col_size는 브로커 파라미터 MAX_STRING_LENGTH가 0 이상이면, 0 이하이거나 그 값보다 클 때 그 값으로 바꾼다.
  • fetch는 CAS가 첫 행 묶음을 붙이는 것이고 그때 시작 위치를 1로, 행 수를 50으로 준다. CALL 플래그로 준비한 문장은 문장 종류가 SELECT가 아니므로 붙이지 않는다. cache_reusable이 1이면 뒤의 필드가 모두 없으므로 행 묶음도 붙지 않는다.
  • 이 응답에 붙는 행 묶음은 CAS 함수 fetch_result가 쓰므로 구조 fetch_rows에서 조건이 붙은 fetched가 항상 온다.
  • include_column_info는 실행한 세션의 문장이 하나뿐이고 column_types_vary가 거짓이면 0이고 그 밖에는 1이다. 저장 프로시저 호출은 column_types_vary를 보지 않는다. column_types_vary는 클라이언트가 V13 이상이고 문장이 SELECT이고 PREPARE 응답에서 타입을 알리지 못한 컬럼이 있을 때 참이다. 그래서 그런 SELECT를 실행할 때마다 V13 이상의 클라이언트는 컬럼 정보를 다시 받는다.
  • CALL 플래그로 준비하지 않은 핸들에서 column_meta가 오면 그 뒤의 행 묶음과 이후의 FETCH 응답은 column_meta의 컬럼 목록을 따른다. V13 이상의 클라이언트에는 PREPARE 응답에서 타입 코드가 NULL이던 컬럼이 실행 결과에서 정해진 타입 코드로 온다.
  • column_meta의 num_markers는 질의 대체 규칙이 맞은 핸들이면 원래 질의의 표시자 수이고, 아니면 준비가 정한 표시자 수다.
  • inserted_oid는 stmt_type이 INSERT이고 결과의 첫 값이 객체이거나, 생성 키를 요청해(CCI_EXEC_RETURN_GENERATED_KEYS) 결과가 객체 하나만 든 시퀀스일 때만 값이 있다. 그 밖에는 세 필드가 0이다.
  • 자동 커밋 모드이면 CAS는 문장을 실행한 뒤 응답을 보내기 전에 커밋한다. 다만 결과 집합을 돌려주는 종류의 문장(SELECT, CALL, GET_STATS, EVALUATE)은 엔진이 마지막 질의를 이미 커밋했다고 알리지 않으면(tran_was_latest_query_committed) 커밋을 미룬다. 미룬 커밋은 행 묶음이 결과의 끝이나 max_row에 닿을 때(구조 fetch_rows의 비고)나 NEXT_RESULT로 결과 집합을 돌려주지 않는 마지막 결과에 넘어갈 때 한다. 다만 핸들이 앞으로만 가는 커서가 아니거나 갱신 가능한 핸들이면 CAS 함수 fetch_result와 NEXT_RESULT는 커밋하지 않으므로 미룬 커밋을 CAS가 하지 않는다. holdable로 준비한 핸들의 CALL 문은 미루지 않는다. 저장 프로시저 호출(CALL 플래그)은 호출이 커서를 돌려주면 미룬다. 표시자가 있는 문장은 이 함수로 실행할 수 없으므로 ? = CALL 꼴이나 OUT 표시자의 경우는 생기지 않는다. 자동 커밋 모드에서 실행이 오류로 끝나면 CAS는 응답을 보내기 전에 롤백하고, 저장 프로시저 호출의 실행 오류에서는 롤백하지 않는다.
  • 핸들이 문장 풀링 중인 핸들이고 CALL 플래그로 준비한 것이 아니며 실행이 ER_QPROC_INVALID_XASLNODE나 ER_HEAP_UNKNOWN_OBJECT로 실패하면 CAS는 CAS_ER_STMT_POOLING 오류로 응답하고 응답을 보내기 전의 커밋이나 롤백을 하지 않는다.
  • 준비가 오류로 끝나면 auto_commit_mode가 1일 때 CAS는 응답을 보내기 전에 롤백한다.
  • 준비가 오류로 끝나면 CAS는 실행하지 않고 오류 응답만 보낸다. 실행이 오류로 끝나면 준비한 서버 핸들을 해제하고 오류 응답을 보낸다.
  • cas_shard_flag가 켜진 CAS는 deferred_close_handle을 읽지 않는다. 핸들 수가 MAX_PREPARED_STMT_COUNT에 이르러도 CAS_ER_MAX_PREPARED_STMT_COUNT_EXCEEDED 오류로 응답하지 않는다. 첫 행 묶음을 싣는 응답 크기의 한도는 NET_BUF_SIZE가 아니라 512KB다.
  • JDBC는 이 요청을 보내지 않는다.

버전별 차이​

버전에 따라 생기거나 없어지는 필드가 없다.
