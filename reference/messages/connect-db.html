CONNECT_DB

CAS가 연결을 넘겨받은 뒤 드라이버가 보내는 데이터베이스 접속 요청과 CAS의 응답

항목내용
대조한 커밋엔진 e30370dc03, JDBC 18d5254624 (2026-11-13)

요청​

순서필드형식크기조건설명
1db_nameBYTES(32)32NUL로 끝나는 문자열이고 CAS는 마지막 바이트를 NUL로 바꿔 읽는다. HEALTH_CHECK_DUMMY_DB(___health_check_dummy_db___)이면 접속하지 않고 상태 확인 응답을 보낸다
2db_userBYTES(32)32NUL로 끝나는 문자열이다. CAS는 마지막 바이트를 NUL로 바꿔 읽고, 비어 있으면 PUBLIC으로 바꾼다
3db_passwdBYTES(32)32NUL로 끝나는 문자열이다. CAS는 마지막 바이트를 NUL로 바꿔 읽는다
4urlBYTES(512)512접속 URL 문자열, NUL 한 바이트, 드라이버 버전 문자열의 길이 한 바이트, 드라이버 버전 문자열, NUL 순서로 앞에서부터 채우고 나머지는 0이다
5db_sessionidBYTES(20)20세션 식별자다. CAS는 앞의 SERVER_SESSION_KEY_SIZE(8)바이트를 서버 세션 키로, 이어지는 4바이트를 네트워크 바이트 순서의 세션 ID로, 나머지 SESSION_SECRET_SIZE(8)바이트를 세션 비밀값으로 읽는다

비고​

  • 이 메시지는 CONNECT_BROKER의 응답으로 0을 받은 뒤에 오간다. TLS 연결이면 그 사이에 TLS 핸드셰이크가 있고 이 요청과 응답은 TLS 위로 오간다. 핸드셰이크 자체의 형식은 적지 않는다.
  • 요청은 CAS 쪽에서 V7 이상이면 항상 628바이트(32, 32, 32, 512, 20)다. CAS는 이만큼을 읽을 때까지 기다리고, 읽지 못하면 오류 응답을 보낸다.
  • db_name이 비어 있으면 CAS가 오류로 응답한다. JDBC는 db_name에 이름을 32바이트까지 복사한다.
  • CAS는 url의 마지막 바이트를 NUL로 바꿔 URL을 읽고, URL 문자열 끝의 NUL 바로 뒤의 한 바이트를 길이로 읽어 1 이상 SRV_CON_VER_STR_MAX_SIZE(20) 미만이면 이어지는 그만큼을 드라이버 버전 문자열로 기록하고, 아니면 PROTOCOL V와 프로토콜 번호로 만든 문자열을 기록한다.
  • JDBC는 url에 URL을 511바이트까지 복사하고, 버전 문자열이 20바이트 이하이며 URL과 버전의 길이에 3을 더한 값이 512 이하일 때만 버전을 싣는다. 길이가 정확히 20이면 JDBC는 싣지만 CAS는 읽지 않는다. URL이 없으면 앞 두 바이트를 0으로 둔다.
  • 요청의 db_sessionid 영역은 NUL로 끝나는 문자열이 아니고 마지막 바이트도 세션 비밀값의 일부다.
  • JDBC는 CAS와 마찬가지로 세션 식별자의 앞 8바이트 다음에 오는 4바이트를 세션 ID로 사용한다. 첫 접속에서 JDBC는 영역의 첫 바이트에 문자 0(0x30)을 넣고 나머지를 0으로 채운다. 이후 다시 연결할 때는 이전 응답으로 받아 저장해 둔 세션 식별자를 그대로 보낸다.
  • 응답은 세 가지 가운데 하나다. CAS가 코드에서 구분하는 순서는 요청을 읽지 못했을 때의 오류, 상태 확인 요청, 접속 시도다. 접속 시도는 접근 제어 검사, 데이터베이스 접속, 성공 응답 순으로 진행하고, 앞의 두 단계에서 실패하면 오류 응답이다. 세 모양 모두 머리의 첫 4바이트가 msg_body_size이고 CAS 정보 4바이트가 바로 뒤에 온다.
  • 이 메시지의 CAS 정보 4바이트는 함수의 응답과 값이 다르다. CAS가 접속 응답을 위해 따로 만든 배열을 사용하므로 additional_flag는 항상 0xFF이고, CAS 정보 status는 오류 응답에서 INACTIVE이며 성공과 상태 확인 응답에서 ACTIVE다. JDBC는 이 4바이트를 그대로 저장해 두었다가 첫 함수 요청의 머리에 싣는다.
  • 프로토콜 버전을 두 곳에서 알린다. 클라이언트는 CONNECT_BROKER 요청의 protocol_version으로 자신의 버전을 알리고, 서버는 이 응답의 broker_proto_version으로 자신의 버전을 알린다. CAS는 클라이언트가 알린 값으로 이 응답의 크기와 구성을 정한다. JDBC는 서버가 알린 값을 자기 쪽 프로토콜 버전으로 사용한다.
  • JDBC는 broker_proto_version에서 읽은 서버의 프로토콜 버전이 V8보다 작으면 지원하지 않는 서버로 보고 연결을 실패시킨다.
  • CAS는 클라이언트가 V12 이상일 때만 broker_system_param의 0x01 비트를 고쳐 쓰고, 그보다 낮으면 고치지 않는다.
  • JDBC는 응답의 db_sessionid를 그대로 저장해 두었다가 다시 연결할 때 요청의 db_sessionid에 넣고, CANCEL과 STATUS 요청에는 앞의 8바이트 다음에 오는 4바이트의 세션 ID를 싣는다.
  • error_code로 알리는 오류가 나는 경우는 다음과 같다. 접속 요청을 끝까지 읽지 못했으면 CAS_ER_COMMUNICATION이다. 접근 제어 목록이 접속을 거부하면 DBMS_ERROR_INDICATOR와 CAS_ER_NOT_AUTHORIZED_CLIENT이고 메시지는 Authorization error.(Address is rejected)다. 데이터베이스 이름이 비어 있으면 CAS_ERROR_INDICATOR와 코드 -1이고 메시지가 없다. 데이터베이스에 접속하지 못하면 DBMS_ERROR_INDICATOR와 엔진의 오류 번호이고 메시지는 엔진의 오류 메시지다.
  • CAS는 클라이언트가 CONNECT_BROKER 요청의 protocol_version에 CAS_PROTO_INDICATOR 비트를, function_flag에 BROKER_RENEWED_ERROR_CODE를 켜서 보냈으면 오류 코드를 그대로 보낸다. 그렇지 않으면 지시자가 CAS_ERROR_INDICATOR이거나 코드가 CAS_ER_NOT_AUTHORIZED_CLIENT일 때 코드에 9000을 더해 보낸다. JDBC는 BROKER_RENEWED_ERROR_CODE를 켜서 보내지만 지시자가 -1이고 코드가 -10000보다 크거나 코드가 -1018이면 error_code에서 9000을 빼서 읽는다.
  • JDBC는 error_message의 마지막 바이트를 뺀 나머지를 메시지로 읽는다.
  • 응답이 오지 않는 경우가 있다. CAS가 TLS 핸드셰이크를 받지 못하면 오류 응답 없이 연결을 닫는다.
  • CAS는 오류 응답이나 상태 확인 응답을 보낸 뒤 연결을 닫는다.
  • JDBC는 접속하지 못했던 호스트에 다시 접속할 수 있는지 확인할 때 상태 확인 요청을 보낸다.
  • CAS는 접속에 성공한 뒤 같은 연결에서 함수 요청을 받기 시작한다.
