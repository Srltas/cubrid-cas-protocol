cas_info

머리에 든 CAS 정보 4바이트의 바이트별 뜻

항목내용
대조한 커밋엔진 e30370dc03, JDBC 18d5254624 (2026-11-13)

필드​

순서필드형식크기조건설명
1statusBYTE1CAS가 함수의 응답을 보낼 때 트랜잭션 안에 있으면 ACTIVE, 아니면 INACTIVE로 채운다. JDBC는 이 값으로 트랜잭션이 열려 있는지 판단한다. 값: CAS 정보의 상태
2reserved_1BYTE1CAS는 항상 CAS_INFO_RESERVED_DEFAULT(0xFF)로 채우고 JDBC는 읽지 않는다
3reserved_2BYTE1CAS는 항상 CAS_INFO_RESERVED_DEFAULT(0xFF)로 채우고 JDBC는 읽지 않는다
4additional_flagBYTE1CAS는 모든 비트를 켠 값에서 NEW_SESSION_ID 비트만 끄고 시작한다. JDBC가 읽는 것은 NEW_SESSION_ID 비트뿐이다. 플래그: CAS 정보의 플래그

비고​

  • CAS 정보는 요청의 머리에도 있다. JDBC는 마지막으로 받은 응답의 CAS 정보를 요청의 머리에 실어 보내고, 트랜잭션을 끝낸 뒤에는 CAS 정보 status를 INACTIVE로 바꿔 둔다. CUBRID용 CAS는 요청의 CAS 정보를 읽지 않는다. 읽는 곳은 샤드 모드에서 PREPARE와 CHECK_CAS를 처리할 때의 FORCE_OUT_TRAN 비트뿐이다.
  • 처리 함수를 부르기 전에 난 오류의 응답에서는 status가 항상 INACTIVE다.
  • CAS는 함수의 응답을 보낼 때 additional_flag의 AUTOCOMMIT 비트를 CAS의 기본 자동 커밋 설정(cci_default_autocommit의 최하위 비트)으로 다시 채운다. net_write_error로 따로 보내는 오류 응답에서는 다시 채우지 않는다.
  • additional_flag의 FORCE_OUT_TRAN 비트는 샤드 모드(cas_shard_flag가 ON)일 때만 끄므로 그렇지 않으면 켜 둔 채로 보낸다.
  • 함수의 응답에서 NEW_SESSION_ID 비트는 CAS가 init_msg_header에서 끈 뒤 다시 켜는 곳이 없다. CONNECT_DB의 응답은 CAS 정보를 따로 만들어 보내므로 이 비트가 켜져 있다. JDBC는 이 비트가 켜지고 브로커가 RECONNECT_WHEN_SERVER_DOWN을 알릴 때 오류 응답의 끝에 20바이트 세션 ID가 붙는다고 읽지만 CUBRID용 CAS는 그렇게 보내지 않는다.
